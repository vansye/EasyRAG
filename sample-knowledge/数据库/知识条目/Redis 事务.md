## 详细

### 概念
Redis 事务允许在一个步骤中执行一组命令，并保证这些命令按顺序连续执行，中间不会被其他客户端的命令插入。与关系型数据库事务不同，Redis 事务不具备严格的 ACID 特性，尤其是缺少回滚机制。

### 重点

#### 一、基本用法
- **MULTI**：标记事务块的开始，后续命令不会立即执行，而是进入队列
- **EXEC**：执行事务块中的所有命令
- **DISCARD**：取消事务，清空命令队列
- **WATCH**：乐观锁，监视一个或多个键，若在 EXEC 之前这些键被修改，则事务执行失败

#### 二、事务特性分析

| 特性 | 支持情况 | 说明 |
| :--- | :--- | :--- |
| 原子性 | 部分支持 | 命令排队成功则全部执行，但执行过程中的错误不会回滚已执行命令 |
| 一致性 | 不支持 | 语法错误导致事务不执行；运行时错误仅跳过错误命令，其他命令继续 |
| 隔离性 | 支持 | 事务中的命令序列化执行，中间不会插入其他命令 |
| 持久性 | 不支持 | 取决于持久化配置（RDB/AOF），非事务特有属性 |

#### 三、与 MySQL 事务的关键差异
- 无回滚：Redis 事务中某条命令执行失败，其他命令仍会继续执行，不会撤销
- 命令错误处理：语法错误（EXEC 前检测到）则整个事务不执行；运行时错误（EXEC 时触发）仅该命令失败
- 性能权衡：Redis 事务设计目标是简单快速，而非强一致性

#### 四、使用建议
- 单纯批量执行命令 → 直接使用 MULTI/EXEC
- 需要乐观锁控制并发 → 配合 WATCH 使用
- 追求原子性且需回滚 → Redis 不适合，考虑 Lua 脚本（可原子执行且支持逻辑判断）
- 高并发场景下避免过度使用 WATCH，可能导致重试开销
