## 详细

### 概念
epoll 是 Linux 内核提供的一种可扩展的 I/O 事件通知机制，用于高效处理大量文件描述符（FD）。它通过注册感兴趣的事件，并在事件发生时主动回调应用程序，避免了无效轮询。

### 重点

#### 一、核心系统调用
- **epoll_create()**：创建 epoll 实例，返回 epoll 专用文件描述符。
- **epoll_ctl()**：向 epoll 实例添加、修改或删除待监听的 FD 及其事件类型。
- **epoll_wait()**：等待事件就绪，返回已触发的事件列表。

#### 二、底层数据结构
- **红黑树（RB-Tree）**：存储所有被监控的 FD，实现高效增删改查。
- **就绪链表（Ready List）**：存储已就绪的 FD（采用双向链表），供 `epoll_wait` 直接返回。

#### 三、触发模式
- **LT（水平触发，默认）**：只要 FD 有未处理的数据，`epoll_wait` 就会持续通知。适合编程简单、防止漏处理的场景。
- **ET（边缘触发，高效）**：只在 FD 状态发生变化的瞬间通知一次。要求程序必须一次性读写完所有数据（通常配合非阻塞 IO），性能更高。

#### 四、与 select/poll 的核心差异

| 对比项         | select / poll       | epoll                 |
| :---------- | :------------------ | :-------------------- |
| **管理方式**    | 线性轮询（每次拷贝全部 FD）     | 事件回调 + 红黑树管理          |
| **FD 数量限制** | 受限（select 默认 1024）  | 受系统最大文件句柄数限制          |
| **数据拷贝**    | 每次调用均从用户态拷贝 FD 集到内核 | 内核与用户态共享内存（mmap），避免拷贝 |
| **时间复杂度**   | O(n)（轮询所有 FD）       | O(1)（仅处理活跃 FD）        |

#### 五、适用场景
- **高并发服务器**：如 Web 服务器（Nginx）、游戏服务端。
- **事件驱动框架**：如 Redis 的事件循环、Libevent。
