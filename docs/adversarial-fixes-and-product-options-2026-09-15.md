**已完成的修复及保留边界**

| 项目 | 原来的可复现问题 | 现在的行为 |
|---|---|---|
| F1：切片容量 | 合法 Markdown 通过上传，却因超长标题或低 token 密度的长正文在保存切片时失败 | 切分和合并同时满足完整 embedding 输入的 token 预算、正文 65,535 个 UTF-8 字节上限；标题路径元数据取前 512 个 Unicode 码点 |
| F1：空白覆盖契约 | 跳过纯空白片段与 A 要求连续覆盖全部字节冲突 | A/B 共同允许首尾及切片间的纯 Unicode 空白间隙，所有非空白字符仍须覆盖 |
| F3：编辑生命周期 | 浏览器后退丢失草稿；A 的异步保存完成后被归到 B | 路由变化统一经过 dirty/busy 规则；保存、删除和重新处理固定开始时的资料 ID；删除完成并解除 busy 后关闭抽屉 |
| F4：状态刷新 | Pinia 开发模式代理身份变化使请求无法合并；旧 READY 或旧网络失败覆盖新状态 | 用稳定的 `$state` 合并刷新；版本号使旧成功和旧失败响应失效；变更后等待旧请求结束并读取新快照 |
| F4：变更入口 | 恢复、保存或上传结束后可能复用变更前的刷新 | 恢复、保存、删除、重新处理和上传均采用 `refreshAfterChange()` |

切片的 `text` 仍是原文精确子串，偏移仍是 UTF-8 字节区间，数据库继续保存完整 `document.content`。允许的空白语义包含 NBSP、NEL 和全角空格；零宽空格属于必须保留的非空白内容。不能依靠拼接切片还原所有原文字节，应读取完整文档。

完整标题仍保留在原文中，只有标题路径元数据限制为 512 个码点。这个决定保留现有数据库字段，代价是超长路径末尾不再进入标题元数据。若标题路径、单个正文字符及特殊 token 已超出配置预算，索引仍明确失败；这次没有承诺所有标题都能适应任意 token 预算。

容量属于固定的跨模块契约，由 B 产出、A 校验，公开文档与跨模块测试保持一致。A/B 的生产代码仍互不 import，未增加动态配置层、通用重试或吞掉错误的兜底逻辑。这些改动对应已复现的输入和时序路径。

F2 仍能用模型替身稳定复现：检索为空时返回 `SUFFICIENT`，系统可继续得到 `ANSWERED / sources=[]`；只有来源 1 时生成 `[9]`，也可能被接受。M4 应由 C 落实无证据拒答与引用编号规则，G 继续负责解析实际来源。编号有效本身也不能证明回答内容正确。

使用当前环境配置的 `agnes-3.0-flash`（`provider=openai`），以及实际 `bge-m3` / 1024 维 embedding、tokenizer、隔离 MySQL 和临时 Chroma，经过真实 Services 与 FastAPI TestClient 链路。输入全是合成资料，没有读取或修改业务知识库，也没有输出或写入模型凭据。

**架构判断与扩展成本**

A 管理持久化事实，B 管理可重建索引，C 管理问答流程，F 管理模型与凭据，G 通过公开接口编排。这套模块化单体的职责划分清楚；本次缺陷来自跨模块数据契约、前端资料身份和状态时序，没有发现必须拆服务才能解决的问题。

新增历史记录的一个具体前置工作是数据库增量升级。[knowledge/_database.py](../rag-service/app/modules/knowledge/_database.py) 将 `REVISION` 固定为 `0001_legacy_v2`，版本检查与初始化主要服务于空库初始化和旧库接管。历史功能需要增加从现有基线升级的迁移路径，并同步版本检查及 schema 验收；仅新增一张表或修改基线迁移不构成完整交付。SQL 仍应留在现有持久化边界，由 G 取出历史并向 C 提供上下文，C 不直接访问数据库。

当前 QUERY 与资料变更互斥，适合个人规模，但索引和长问答会相互影响。未来会话必须按每次提问取得、释放许可，不能让整个会话占用许可，否则用户停留在聊天页面就会阻塞资料变更。忙碌时上传可能保留 PENDING、需要手动重新提交的现有取舍继续保留；若后续导入频率增加，可在现有进程内改进调度，不必先引入消息中间件。

以下工期是熟悉本项目的一名单人开发者完成实现、迁移与必要测试的粗估，用于比较范围，不是排期承诺。

| 需求 | 业务价值与必要性 | 推荐首版 | 主要代价 | 建议 |
|---|---|---|---|---|
| 问答历史 | 找回答案、比较资料变化前后的结果，减少重复提问；当前价值最直接 | 独立问答记录、列表/详情、删除、基于当前资料重新提问 | 约 3–5 人日；数据库增量迁移及证据快照存储；查看记录不增加模型调用 | 优先做 |
| 上下文多轮问答 | 支持“它呢”“再比较一下”等追问，减少重复输入 | 有长度边界的上下文，必要时改写独立问题，再检索当前资料 | 历史完成后约增加 3–7 人日；上下文 token、改写调用与评估成本 | 历史之后做 |
| 自主工具 Agent | 适用于确实需要规划、跨工具或多步检索的任务；当前还缺收益证据 | 先在 M4 对照评估一次有界改写/重查的效果 | 循环、停止条件、工具行为、额外模型调用及可追踪性，范围波动较大 | 暂缓完整实现 |
| Obsidian 轻量插件 | 在写笔记时直接提问、收录和查看出处；必要性取决于它是否是日常主入口 | 选区提问、手动收录/更新当前笔记、打开引用 | API 稳定后约 3–5 人日；插件适配和笔记身份映射 | 可选第二客户端，可独立于 Agent 开发 |
| Obsidian 全库同步 | 对大量笔记持续同步有用，偶尔收录时收益有限 | 先定义 vault 为真相源，再覆盖重命名、删除和冲突 | 在轻量插件基础上约增加 1–2 周或更多 | 单独立项，避免混入插件首版 |

历史记录应保存当次问题、答案与状态、时间、模型信息、trace，以及来源正文快照、排名与必要的文档版本/定位信息。只保存 `chunk_id` 不足以还原历史：修改或删除文档后，切片会变化或消失。快照只保存当次来源片段即可，无需复制整份知识库。

建议将“查看历史”定义为查看当时的问答，将“重新提问”定义为基于当前知识库生成新结果。资料删除后，历史可保留当时快照并标注来源已删除，历史提供独立删除入口；彻底清除资料正文时也应纳入对应历史快照。生成答案不自动进入资料索引，避免答案再次成为自身的检索依据。快照使历史可还原，不会自动修复 F2 的回答可信性缺口。

上下文追问可以沿用当前 C 的有界流程。G 读取有限历史，C 使用它理解省略和指代，再根据当前资料作答。当前一次生成型问答通常为“判定 + 生成”两次模型调用，拒答通常一次；独立问题改写可能再增加一次，额外一轮检索改写与重判可能再增加两次。完整历史持续拼接也会增加 token，因此首版应明确上下文取舍，而不是默认开启无界循环。

Obsidian 插件复用 FastAPI，核心功能仍支持普通 Markdown 和 Web。当前 `source_uri` 的上传文件名不足以可靠识别 vault 内的笔记，需要稳定的 vault/路径与 document ID 映射，手动更新时也应复用这份映射。全量同步进一步涉及重命名、删除和网页编辑冲突；如果选择 vault 为真相源，网页编辑应据此定义行为。

插件不会消除现有 FastAPI、MySQL 和 Ollama 的运行成本。桌面端本机插件的工期不包含移动端或远程服务访问。是否先做插件取决于实际笔记工作流，与是否实现自主 Agent 没有依赖关系。

建议的实施顺序是：问答历史与数据库升级 → M4 回答约束和检索评估 → 上下文追问；轻量 Obsidian 插件在接口稳定、使用频率足够时插入。只有评估证明多步工具调用带来实际收益，再推进完整 Agent。三个新需求本轮仅完成评估，没有实现。
