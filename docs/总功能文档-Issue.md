# 总功能文档：EasyRAG 个人知识库问答系统

> 本 Issue 是功能总纲：定义产品边界与模块划分。每个模块的详细设计（功能描述、数据原型伪代码、对外接口伪代码、模块边界说明）在子 Issue 中展开，挂在本 Issue 下。

## 一、背景

收藏 ≠ 拥有：资料越攒越多、散落各处，无法检索与调用。本项目做一个能管理和调用知识的系统——随手丢进去，用一句话问出来，答案附出处。

## 二、产品定义

一个网页，三件事：

1. **收录与管理资料**：md / txt / 链接，支持更新与删除
2. **问答**：一句话提问 → 答案 + 可点开的出处（定位到文档与位置）
3. **更新同步**：资料更新或删除后，问答结果随之更新

拒答是一等行为：检索质量不足时返回"库里没有"，不进入生成。

## 三、功能边界

### 做（范围内）

- 资料收录（md / txt / URL）、列表、更新、删除
- 切片、embedding、检索、agent 多步检索
- 带出处的问答、拒答
- 黄金问答集与评估（hit@k / 拒答正确率）
- 检索过程展示（重查次数、采用/丢弃的片段）

### 不做（范围外）

| 项 | 理由 |
|---|---|
| 资料编辑器 / 阅读器 | 编辑发生在本地工具，系统只收录与管理 |
| 登录、多用户、权限 | 单用户工具 |
| 流式输出 | 对问答价值低，非考点 |
| PDF / Word 富格式解析 | 主知识形态为 md 与网页；解析工程量大、不增加检索深度（后续可作扩展） |
| Obsidian 插件形态 | 网页形态覆盖不依赖 Obsidian 的用户；RAG 服务独立于 UI 形态，插件可作为后续第二客户端接入同一套 API |

### 已定（原待定项的裁决）

- **收录入口形态：网页上传优先**。理由：网页形态覆盖面广（不依赖用户使用 Obsidian）；后续可向 Obsidian 插件方向演化——RAG 服务独立于 UI 形态，插件可作为第二客户端接入同一套 API。文件夹同步（以文件夹为真相源）暂不做，数据模型以 `source` 字段预留，实施遇阻或需要贴近本地知识库使用习惯时再启用。

## 四、模块划分（各对应一个子 Issue）

| 模块 | 位置 | 职责 |
|---|---|---|
| **A 资料管理** | Spring Boot | 资料收录、内容哈希与变更检测、chunk 元数据落库、触发重索引、对外全部 REST API |
| **B 索引管线** | Python（Java 编排） | 切片策略、embedding、向量与词法索引的构建与失效、全量重建 |
| **C 问答 Agent** | Python | 检索、查询改写与多轮重查、拒答判定、带引用生成、检索 trace |
| **D 评估** | 跨栈 | 黄金问答集管理、跑集（hit@k / 拒答正确率）、结果存储与展示 |
| **E 前端** | Vue | 收录/管理界面、问答界面（答案 + 出处 + 检索过程） |

模块间通信两条边界：**前端 ↔ Spring Boot（REST）**、**Spring Boot ↔ Python（内部 HTTP）**。Python 不直接暴露给前端，不直接读写 MySQL。

写入流的编排次序（模块 A ↔ B）：Java 发原文 → Python 切片返回 chunks → Java 落库（chunk 文本与元数据）→ Java 携 chunks 二次调用 → Python 做 embedding 并更新派生索引。MySQL 只有一个写入者。

## 六、架构不变量

1. **MySQL 是唯一真相源**：资料、chunk 文本与元数据、黄金集、评估结果、检索 trace 全部在 MySQL，且只有 Spring Boot 写入。
2. **派生索引可重建**：向量与词法索引按 chunk_id 关联 MySQL，丢失即重算，不构成事故。
3. **溯源链路贯穿全程**：chunk_id 从索引带到 API 响应，中途不丢。
4. **拒答是一等行为**：检索质量不足时不进入生成。
