## 二之二、部分覆盖类（1 题，库中有相关片段但不足以完整回答）

| # | 问题 | 库中实际有什么 | 缺什么 |
|---|---|---|---|
| P1 | 什么是 Transformer 的多头注意力机制？ | `KV Cache.md` §五.1 有一句定义性描述：「**MHA（传统多头）**：每个注意力头都有独立的 K、V，Cache 极大」，以及 MQA/GQA 的对比 | 多头注意力的完整原理：Q/K/V 如何投影、注意力如何计算、为什么要多个头、多头输出如何拼接。库中这段是在**显存优化**的语境下提到 MHA，不是在讲注意力机制本身 |

**期望行为**：不是拒答，也不是当作直答——而是**基于已有片段回答 + 明确声明覆盖边界**。合格的回答形如：

> 库中在 KV Cache 的显存优化语境下提到：MHA（传统多头）指每个注意力头拥有独立的 K、V。但知识库没有涵盖多头注意力的完整原理（如 Q/K/V 投影与注意力计算过程）。[出处：KV Cache.md]

### 为什么要单立这一类

知识覆盖不是"有/无"二元的。真实知识库里大量话题处于"提了一句但不成体系"的状态——尤其是笔记这种形态，作者常在讲 A 时顺带提到 B。二元拒答无法表达这种状态，会逼出两种都错的行为：

- **判成库外 → 拒答**：明明有相关内容却说"库里没有"，用户会觉得系统没用（而且这内容是他自己记的）
- **判成直答 → 照答**：拿一句显存优化语境下的描述当作注意力机制的完整解释，等于用片面信息冒充完整答案

这一类的存在把"拒答"从一个开关变成**有层次的判断**，也是「知识库里没有的内容，系统会怎样」这个问题的完整答案：分三种情况，而不是一句"说没有"。

### 判定标准（三个条件全满足才算部分覆盖）

定这个标准前实测过两条更省事的路，**都不成立**：

| 尝试 | 实测结果 | 结论 |
|---|---|---|
| 用 top-1 相似度阈值划分 | 直答 Q1 = 0.579，部分覆盖 P1 = **0.588**（比直答还高），库外 = 0.45 / 0.32 | 相似度能分开"库外"，**分不开"直答"与"部分覆盖"**——因为 P1 的片段确实高度相关 |
| 用"子方面覆盖数"划分 | 直答 4/4，部分覆盖 3/4，且那 3 个里有两个是词面相近的假高分（「注意力如何计算 QKV」匹配到了 PagedAttention 显存分页） | 差距太小且不可靠，阈值调不出稳定边界 |

所以判定**必须由 LLM 做**——它是唯一能回答"这段文字是否足以回答这个问题"的东西。这不是偷懒，是实测排除了确定性方案后的结论。

标注一道题为"部分覆盖"，需同时满足：

1. **检索得到的 top-k 中，至少一个片段与问题主题直接相关**（不是词面巧合）。P1 里 MHA 那句就是——它确实在讲多头注意力。
2. **该片段无法支撑一个完整回答**：把片段单独交给 LLM 并问"仅凭这段，能完整回答原问题吗"，答案为否。P1 中缺的是 Q/K/V 投影与注意力计算这些核心机制。
3. **缺失部分是问题的主体，不是边角**。若只缺一个次要细节（如某个参数的默认值），仍算直答类——那是回答不完美，不是覆盖不足。

三条里第 2 条是判定的核心，第 1、3 条是护栏：没有第 1 条会把库外题误收进来，没有第 3 条会让这一类无限膨胀、吞掉直答类。

### 系统运行时怎么判（M3 实现）

评估时的标注是人工的（依上述三条），但**系统在线运行时不能靠人工**。运行时判定放在生成阶段之前，用一次结构化判断：把 top-k 片段与问题一起交给 LLM，要求输出三态之一——

```
SUFFICIENT  -> 正常带出处回答
PARTIAL     -> 回答 + 声明缺什么（本类的期望行为）
NONE        -> 拒答
```

这个三态判定就是 agent 循环里"一步答不好"的落点之一：判为 PARTIAL 时可以先尝试改写重查（也许别处还有更完整的内容），重查后仍是 PARTIAL 才输出带边界声明的答案。这条链路正面回答已预告的追问③「为什么需要多步流程，一次检索加一次问答不行吗」。

**评分口径**：本类的正确 = 系统判为 PARTIAL 且答案中包含边界声明。判成 SUFFICIENT（照答不声明）或 NONE（该有内容却拒答）均记错。

**当前只有 1 题**，样本量不足以支撑统计结论，它的作用是**把这个设计问题显式化并给出一个可回归的例子**。M2 基线跑通后按同样三条判据从语料中再找几道补齐——`KV Cache.md` 里的 PagedAttention、FlashAttention 也是同类候选（提了机制名但没讲原理）。

## 四、格式说明

- 正式入库后每题一行记录（question / expected_doc / expected_chunk_hint / category），由模块 D 的评估脚本消费。
- 直答类的“正确出处”是唯一标准答案：hit@k 只认标注文档（chunk 命中即算命中，k=5）。
- 库外类的标准答案 = 系统返回拒答（不返回编造内容）。
- 部分覆盖类的标准答案 = 系统判为 PARTIAL，回答中包含边界声明（判成照答或拒答均记错）。
- 需改写类既测检索（最终能命中标注文档），也测多轮行为（trace 中应出现重查/改写步骤）。

### 命中口径的一条说明

**命中同主题的次要文档记为 miss。** 例如 Q13（拦截器 vs 过滤器）标注的出处是 `Interceptor拦截器技术.md`（有专门一节讲与 Filter 的区别、含容器层级图），而 `知识条目/后端/Interceptor拦截器.md` 是一张概念卡片，写了「比 Filter 更贴近 Spring」并主动把细节让给前者——它能提供部分正确信息，但检索命中它仍算 miss。

这是刻意的：本指标测的是**"找到最佳答案"**，不是"找到相关内容"。真实知识库里「概念卡 + 详解」成对存在是常态，能否在两篇同主题笔记中挑出信息更全的那篇，正是检索质量的一部分。

副作用是首次跑基线时分数会偏低，看到数字不要误判成检索坏了。

## 五、维护规则

- 题目总数固定 30（四类比例 16:7:1:6），后续改进以“同集重跑看数字变化”为口径——改检索后改题集，等于换了度量衡再比身高。
- 发现某题标注错误（出处不唯一 / 库外题其实有答案）→ 修题 PR 说明理由。评估集本身也要可审计。
