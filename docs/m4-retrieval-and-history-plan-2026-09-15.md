优先级 1 的实施契约（C #27、B #3、G #36，评估口径 D #37）：

- 检索返回空证据时直接 `REFUSED`，本轮 trace 为 `NONE`，判定与生成均不调用模型。非空证据的 `NONE` 保留 1 次判定；`SUFFICIENT/PARTIAL` 保留判定、生成各 1 次。
- 生成答案必须至少含一个正文引用，所有正文引用编号必须落在本轮候选的 `1..k` 内。无引用、越界、有效与无效混合的结果统一 `QaError(generate, INVALID_CITATIONS)`，HTTP 502，不查出处、不保存成功历史、不自动重试。`REFUSED` 只表示无依据，`PARTIAL` 只表示覆盖不足，不能用来隐藏模型输出错误。
- 引用遵循已有 Markdown 展示语义：支持 `[1]`、逗号分组与递增区间；代码块、行内代码、链接、图片、HTML 和转义文本中的数字不充当正文引用。用前后端共享样例验证。`sources` 仍保存所有提供给生成器的依据，编号仍按最终检索 rank，不删改原答案或缩减来源集合。
- B、C 通过可选计时回调返回阶段耗时，G 每问独立聚合为一条日志；业务模块互不引用。记录会话准备、embedding、向量索引、判定、生成、出处查询、历史保存及总耗时。索引耗时包含 embedding 前的索引探测和随后查询，保持原执行顺序。未执行的阶段为 `null`，失败阶段仍记录已消耗时间。
- 原 `elapsed_ms` 继续截止历史写入前；新增日志 `total_ms` 截止历史提交后，不含浏览器网络/渲染。日志只含计时、结果和安全错误分类，不记录问题、答案、来源、地址或凭据。本项不修改历史 schema 和 HTTP 成功响应。

交付按功能区分：UI 布局与浏览器 CI、C 回答约束、B/C/G 计时。功能 PR 引用对应模块 Issue，不提前关闭整个模块；检索改进阶段仍必须报告前后评估数字，不能把本阶段的规则修复称为 hit@k 提升。

**“不写算法就难找”怎样定位**

这类现象至少需要区分三条路径：正确片段没有进入候选；正确文档被命中但片段不足或排序靠后；材料已足够但判定器/生成器没有正确使用。优化应对应实际失败环节。重排只能处理已经召回的候选，不能补回候选集合中完全不存在的资料。

当前未自动使用文件标题和标签扩展查询语义。如果题意只在文件名里、长代码被分到缺少题意的片段、或原问题本身具有多种含义，都值得检查。把文档标题加入 embedding 也需要同步 token 预算并重建索引，不能未经评估直接拼接。上传材料本身是否包含足够的题意与解法，也应和问法一起看。

本轮用 16 份合成资料组成混合知识库，包括 8 份算法笔记、桌面窗口、TCP 窗口及其他干扰资料，得到 16 个切片。两组问法的实际结果为：

| 合成问法 | 正确资料排名 | 正确资料 score |
|---|---:|---:|
| 字符串里最长不重复的连续部分怎么求？ | 1 | 0.7121 |
| 算法题：字符串里最长不重复的连续部分怎么求？ | 1 | 0.6909 |
| 一个数组中找两个加起来等于目标值的不同位置，怎么做？ | 1 | 0.6520 |
| 算法题：一个数组中找两个加起来等于目标值的不同位置，怎么做？ | 2 | 0.6366 |

四次问答都得到 ANSWERED，生成器使用了正确来源；最后一题正确来源编号为 [2]。这些合成样例说明无需建立“没有算法二字就自动补算法”的规则。用户报告的真实失败尚未复现，已请求原问题、加词后的问题与期望笔记标题，后续用实际样例区分上述路径。

**Agentic RAG 的三个范围**

| 方案 | 收益适用条件 | 延迟和实现成本 | 本项目建议 |
|---|---|---|---|
| 保留单轮检索，评估标题信息或词法/向量融合 | 专有名词、题号、函数名、标题线索未被充分利用 | 不额外调用生成模型；需要语料和排序评估，元数据变化可能需要重建 | 先按失败类型选择实验，BM25 不因进入 M4 就默认上线 |
| 最多一次改写与重查 | 原问法与资料表达不一致，首次证据不足，改写后能增加有效证据 | 可沿用 C 的有界流程，不需要通用 Agent 框架；困难问题增加调用 | 作为 M4 对照实验 |
| 通用自主 Agent，多工具、多轮规划 | 确实需要跨工具执行或开放式研究 | 延迟、成本、停止条件、工具语义和评估范围都更大 | 当前暂缓 |

推荐的有界流程是“原问题检索 → 判定 → 有充分证据即生成；证据不足时按明确规则最多改写一次并重查 → 最终回答或拒答”。改写不得擅自添加题目约束或假定用户未提供的背景；真正缺少指代对象的问题需要澄清。

当前生成型问答为判定 + 生成两次模型调用。若单独增加改写，再做一次判定，困难路径可能增加到四次调用；普通问题应保持原来的两次。也可实验让第一次判定在证据不足时同时给出检索改写，减少独立调用，但它会改变判定输出契约，需要单独验证。模型错误地判为 SUFFICIENT 时，上述不足触发机制仍可能漏掉问题。

因此，本项目可以做轻量的单问题 Agentic RAG，但应以“新增有效证据/正确回答的比例”和额外延迟证明价值。它不依赖多轮聊天、对话记忆或 Obsidian 插件。

**真实耗时实验**

本轮使用当前配置 agnes-3.0-flash（provider=openai）与实际 bge-m3 / 1024 维 embedding、tokenizer、隔离 MySQL 和临时 Chroma。全链路通过 FastAPI TestClient，输入仅为合成资料，不读取业务知识库。7 次完整问答共 13 次模型调用；另做 4 次生成流式试验，共计 17 次真实模型调用。

计时边界为本地应用内部，未包含真实浏览器到服务器的网络和页面渲染。模型调用耗时包含服务端排队、输入处理、推理/生成、传输和 SDK 开销；现有返回信息不足以将“思考”和“输出”可靠拆成独立数字。

同一个最长子串问题的第二次请求（热请求）：

| 阶段 | 实测耗时 |
|---|---:|
| 本次模型会话构造 | 0.005 秒 |
| 问题 embedding，含本地 HTTP 客户端建立 | 0.659 秒 |
| 向量查询，含 collection.count 与结果转换 | 0.002 秒 |
| 覆盖度判定模型调用 | 0.460 秒 |
| 答案生成模型调用 | 5.785 秒 |
| MySQL 出处查询 | 0.002 秒 |
| 其余应用/HTTP 编排 | 0.004 秒 |
| 总计 | 6.918 秒 |

5 个热生成型请求的阶段中位数：embedding 0.792 秒、向量查询 0.003 秒、判定 0.502 秒、生成 6.178 秒、出处查询 0.002 秒，整体中位数 7.803 秒。不同阶段中位数不能相加当作同一条请求。

首次请求总耗时 15.083 秒，其中模型会话首次构造 4.437 秒；后续会话构造中位数约 0.007 秒。embedding 客户端建立中位数约 0.032 秒，远小于生成调用。Ollama 返回的 load_duration 在这些请求中约为半秒，但这不足以断言模型每次都被卸载，后续需结合运行状态核查。

库外问题正确 REFUSED，共 1.532 秒，其中 embedding 0.780 秒、判定 0.743 秒，没有调用生成器。该样本有非空但不相关的候选，不能直接套用“空证据立即拒答”的优化。

**流式与简洁回答实验**

使用相同的已检索证据和现有生成提示，通过同一模型 SDK 的 stream 接口逐段接收内容。此实验直接测量生成阶段，没有重复计入 embedding 或判定。

| 试验 | 首段非空文本 | 完整生成 | 输出字符数 |
|---|---:|---:|---:|
| 默认提示，第 1 次 | 8.157 秒 | 11.111 秒 | 519 |
| 简洁提示，第 1 次 | 0.505 秒 | 6.093 秒 | 357 |
| 默认提示，第 2 次 | 0.392 秒 | 4.537 秒 | 555 |
| 简洁提示，第 2 次 | 0.444 秒 | 4.772 秒 | 416 |

四个答案都保留了有效 [1] 引用、最后位置记录、左边界不倒退的要点以及 O(n) 时间复杂度。它们属于一个算法问题的有限检查，不能证明全语料准确率不变。

流式确实能较早显示内容，但无法消除首字前的服务端等待。网页的实际首字时间还需要加上检索和判定。首次流式请求的高首字耗时应保留在报告中，不能只展示后面的快样本。

简洁提示在两组样本中分别减少约 31% 和 25% 的输出字符，但总耗时没有稳定下降，第二组简洁回答反而略慢。可以把减少重复表达作为候选优化，不能据此承诺固定提速。不要用硬截断答案或统一降低 top_k 换取表面速度。

**M4 建议顺序及验收条件**

| 优先级 | 工作 | 主要收益 | 验收边界 |
|---|---|---|---|
| 1 | 补齐空证据拒答与无效引用规则，增加分段计时 | 修复已知业务缺口；空证据路径减少无意义模型调用；可以定位真实瓶颈 | 空证据不能 ANSWERED；无效编号不能成为有效引用；正常/部分/拒答行为保持；不打印凭据 |
| 2 | 把首次 SDK 准备移到合适的就绪阶段 | 降低第一次提问的本地初始化等待 | 不发送预热生成请求、不强制模型配置作为服务启动条件；仍一问固定一份配置 |
| 3 | 打通 F → C/G → HTTP → 前端的流式输出 | 改善看到首字的时间；保持原检索和模型判定 | 固定来源编号；完成后校验引用；区分首字与完整结果；连接结束释放单次查询许可 |
| 4 | 评估简洁默认回答及重复证据压缩 | 减少输出和输入 token | 保留关键条件、边界与引用；详细提问仍提供完整解释；先验证再变更默认行为 |
| 5 | 真实失败例上的标题/词法融合、有界改写重查对照 | 提升困难问法的召回与证据覆盖 | 原有通过题不新增错误；独立难例有收益；记录每题额外调用与耗时 |
| 暂缓 | 新向量库、通用 Agent 框架、每题多路 LLM 改写、仅按分数跳过判定 | 当前缺乏收益证据或增加热路径成本 | 需要新的瓶颈或质量证据再考虑 |

SDK 准备、连接管理和流式传输可以保持相同的资料、检索输入和生成提示，优先于改变召回行为。流式应先完成必要的证据与编号映射；历史记录只在整次结果完成时落库，部分输出不冒充已完成记录。

embedding 客户端复用在本轮主要只涉及几十毫秒，不作为首要工作。可以继续核查 bge-m3 的驻留/加载行为；保持同一模型、维度与文本输入时，才有机会减少运行开销而保持向量语义。当前没有证据支持为了几毫秒的索引耗时更换向量数据库。

精度验收同时包含文档命中、真正能支持答案的片段、排名、三态判定与引用。保留原黄金集，再补实际算法难例、部分覆盖、库外及代码密集笔记，留出未用于调参的样例。比较 hit@5、MRR、证据覆盖、回答/拒答正确性、引用有效性，并记录冷/热请求、首字、完整耗时、token 与改写触发率。以基线通过题无新增错误和独立难例收益作为合入条件，而不是宣称对任意问题保证精度。

**问答历史首版设计**

建议采用现有 MySQL 持久化，每条记录对应一次独立问答，不创建 Conversation/Turn/Agent 等额外抽象。最小行为为：按时间倒序分页查看、打开历史答案及当时出处、删除单条历史、将原问题重新提交。查看历史不调用模型；重新提交使用当前资料并产生新记录。

保存问题、答案、ANSWERED/PARTIAL/REFUSED 状态、时间、实际模型身份、耗时、trace 和来源快照。技术失败不伪装成已完成历史。模型身份从本次冻结会话取得，避免读取另一份恰好更新过的配置。快照包含当时来源正文、标题、编号和定位信息，不能只存会变化的 chunk_id。

历史详情默认展示当时快照，明确区别于当前文档。更新、删除原资料不会让旧回答跳到新切片或丢失原证据；删除历史不修改知识库。历史不自动作为后续提问上下文，也不自动加入资料索引。若以后提供“彻底清除资料内容”，清理范围需要包含相应历史快照。

A 继续独占 SQL，G 负责把问答结果转换为记录，C 保持与持久化无关。增加一张历史表和新的 Alembic 迁移，保留已经执行过的 0001 基线不动，补齐现有基线到新版本的显式升级入口。完成结果保存后再返回成功；保存失败沿用明确失败语义，不自动再调用模型或另建隐式存储。

轻量的浏览器本地历史通常可以缩小改动，但清理浏览器后会丢失，也无法由后续客户端复用。本项目已把知识数据保存在服务端，推荐按 MySQL 方案继续，工期仍按约 3–5 人日粗估。
